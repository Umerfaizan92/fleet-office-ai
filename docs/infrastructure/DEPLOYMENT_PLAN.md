# Deployment plan: environments, release steps, rollback and recovery

The current production service (`super-pro-ai-office-manager`, `render.yaml`) is not changed by this branch. Nothing in it is redeployed until the founder does so by hand.

## Environments

| | Development | Staging | Production |
| --- | --- | --- | --- |
| Where | Your computer (`npm start`) | New Render service from `render.staging.yaml` | Existing Render service from `render.yaml` |
| Data | Throwaway local SQLite | Synthetic test businesses only | Real subscribers |
| Database disk | `./data` | Own 1 GB disk `super-pro-staging-data` | Existing 10 GB disk `super-pro-data` |
| S3 | None or a personal test bucket | Own staging backup bucket and own staging files bucket | Production backup bucket; production files bucket when approved |
| Secrets | `.env` (never committed) | Generated by Render for staging; never copied from production | Existing |
| Phase 02 rules | Off | All on (MFA enforced, 30/90-day sessions, strict passwords, S3 files, JSON logs) | Turned on one at a time after staging |
| Deploys | Any time | Manual, from the release branch | Manual, from `main`, outside business hours |

A staging service costs money (paid plan for the disk). Create it only after reviewing the cost in Render. The existing free preview (`superpro-ai-v2-preview-20261029`) stays as a disposable review copy.

## Release steps

1. **Branch and CI.** Push the branch; GitHub Actions must pass both `CI` (verify-all, UI tests, integration, smoke, audit, secret scan, restore drill) and `Security` (audit, secrets, dependency review, CodeQL).
2. **Staging deploy.** Render → staging service → Manual Deploy → the branch. Then `npm run deploy:check -- https://<staging-url>` from your computer or the shell.
3. **Staging acceptance.** Sign in as the founder with the authenticator; run `npm run storage:verify -- --write-test` and `npm run backup:restore-drill` in the staging shell; upload a job photo; check Founder Console → Operations → jobs and system.
4. **Production backup.** In the production shell, take the manual SQLite backup from `docs/DEPLOY.md` step 1, and note the current deploy in Render → Deploys.
5. **Merge and deploy production.** Merge the pull request to `main`; Render → production → Manual Deploy → latest commit.
6. **Production check.** `npm run deploy:check -- https://super-pro-ai-office-manager.onrender.com` (add `OPERATOR_TOKEN` for full diagnostics). Any FAIL → roll back.
7. **Turn rules on one at a time** (each a separate environment change and redeploy, checked with step 6):
   1. `OPERATOR_TOTP_SECRET` (generate with `npm run generate:operator-mfa`), sign in with a code, then `REQUIRE_OPERATOR_MFA=1`.
   2. `SESSION_TTL_DAYS=30`, `SESSION_MAX_AGE_DAYS=90`.
   3. `LOG_FORMAT=json`.
   4. `STRICT_PASSWORD_MATCH=1` after telling subscribers.
   5. Primary S3 storage after `docs/infrastructure/STORAGE.md` steps.
   6. `CLAMAV_HOST`, then `MALWARE_SCAN_REQUIRED=1`.

## Health checks

| Check | Path | Used by |
| --- | --- | --- |
| Liveness | `/healthz` | Render health check (unchanged) |
| Readiness | `/readyz` (database answers, no background job overdue by 15 min) | `npm run deploy:check` |
| Diagnostics | `/api/saas/health/diagnostics` (founder) | deploy check with `OPERATOR_TOKEN`; now also reports sign-in posture |
| System | `/api/operator/system` (founder, operations permission) | Founder Console |

## Rollback

| Problem | Action | Time |
| --- | --- | --- |
| Deploy check fails, errors rise | Render → Deploys → previous deploy → Rollback. The database only gained a table and indexes, which the previous code ignores. | ~3 min |
| A switched-on rule causes trouble | Remove that one environment setting and redeploy. Every rule is independent. | ~5 min |
| Founder locked out by `REQUIRE_OPERATOR_MFA` | Remove `REQUIRE_OPERATOR_MFA` in Render → Environment and redeploy; sign in with key and code. | ~5 min |
| Primary S3 unavailable | Uploads answer "storage is being set up"; existing files on disk still work. Set `OBJECT_STORAGE_MODE=disk` to accept uploads on disk again; files already in S3 stay readable once S3 is back. | ~5 min |
| Bad data written | Do not roll the database back blindly. Restore the latest backup into a separate service with the restore drill, compare, then copy back only what is needed (see `docs/DEPLOY.md` §6). | hours |

## Disaster recovery

| Scenario | Recovery point | Recovery time | Steps |
| --- | --- | --- | --- |
| Render disk lost or service deleted | ≤ 5 s of writes (Litestream) and ≤ 2 min of uploads | ~30 min | Create a service from `render.yaml` with the same environment; on first start `scripts/start.mjs` restores the database and uploads from S3 automatically, then serves. |
| Accidental change found within 72 h | point in time | ~1 h | Litestream restore to a timestamp into a staging service (`litestream restore -timestamp …`), verify, then copy back the affected rows. |
| Older mistake | daily versions (with bucket versioning) | hours | Restore an earlier object version of the Litestream snapshot, then as above. |
| S3 bucket compromised | — | — | Versioning and the no-delete IAM policy prevent silent loss; rotate the backup IAM key, review CloudTrail, restore from versions. |
| Region outage (Singapore Render) | ≤ 5 s | ~1 h | Same as "disk lost", in another Render region; S3 in Sydney is unaffected. |

Run a recovery rehearsal every quarter in staging and record it in F07.

## Automated security checks (now in the repository)

- `CI` workflow: secret scan, `npm audit --audit-level=high`, the full test suite including route guards, tenant isolation, storage and the restore drill.
- `Security` workflow: weekly and on every pull request — dependency audit, secret scan, policy JSON validation, GitHub dependency review, CodeQL `security-extended`.
- Dependabot: weekly npm updates (AWS SDK grouped), monthly GitHub Actions updates.
